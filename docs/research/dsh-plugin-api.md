## Answers

### A. Plugin package structure

**A minimal DSH plugin is an ordinary npm package plus a `dsh` manifest block.** There are two shapes, and they compose:

| Shape | Requires | What it does |
|---|---|---|
| **Bundle** (Host) | `dsh.bundle.patch` | Declares a YAML patch that inserts Loader entries. |
| **Client half** | `dsh.client` + a `./client` export | Browser UI loaded lazily from a served bundle. |

**Host-only bundle, verbatim from the official authoring skill** (`dsh-agent-preset\skills\cordis-plugin-development\references\host-plugin.md` L9–27):

```json
{
  "name": "@local/my-plugin",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./index.js" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

```yaml
- insert:
    - id: my-plugin
      name: '@local/my-plugin'
      config: {}
```

"*A Host-only bundle needs no dependencies, install scripts, or build tool.*"

**Host + Client bundle, the shipped four-file scaffold** (`…\cordis-plugin-development\templates\decoration\package.json`):

```json
{
  "name": "@local/my-decoration",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./index.js", "./client": "./client.js" },
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": {
      "platform": "web",
      "immediately": true,
      "inject": ["@deepseek-ai/dsh-client-ui-conversation"]
    }
  }
}
```

#### Manifest keys (`dsh-package-manifest`, README L34–43, L50–53)

```ts
const manifest: DshPackageManifest = {
  name: 'example-dsh-plugin',
  version: '1.0.0',
  engines: { node: '>=24', dsh: '0.1.5-alpha.1' },
  dsh: {
    manifestVersion: 1,
    bundle: { patch: './cordis.patch.yml' },
    client,
  },
}
```

- `name`, `version` — **required**.
- `dsh.manifestVersion` — optional; *"the declared format is `1`"*. Defaults are **not** inferred.
- `engines.dsh` — optional SemVer range of compatible DSH versions.
- `dsh.bundle.patch` — one path or an ordered list, each relative to the package root; *"the launcher applies a list in order as one bundle layer."*
- `dsh.client` — `{ platform: 'web', immediately?, inject?, external? }`. `platform` is required (README example: `const client: DshClientManifest = { platform: 'web' }`).
- Top-level `icon` — path relative to manifest dir; *"SVG, PNG, JPEG, and WebP up to 256 KiB are accepted, while absolute paths, URLs, paths outside the directory, and symlinks leaving it are rejected."*
- Display text lives in `locale/en.json` (and `locale/zh.json`) as a `meta` object — `{ "meta": { "title": "…", "description": "…" } }` — read *"without activating the plugin."* Verified shape against the shipped example `C:\Users\haoch\.dsh\profiles\desktop\node_modules\dshmarket\locale\en.json`, which is `{ "meta": {} }` (empty, so this plugin falls back to `package.json` `name`/`description`).

#### Host half vs client half

- **Host half** = the package entry (`main` / `exports["."]`). Exports **one of** (`host-plugin.md` L47–52):
  - `export function apply(ctx, config) {}` with optional `export const inject = ['tools']` and `export const Config`; **or**
  - a service class as the **default** export.
  - *"do not mix them."*
- **Client half** = the `./client` subpath export, declared through `dsh.client`. The browser artifact *"registers a lazy factory whose id equals the package name"* (`ui-plugin.md` L9). Real scaffold (`templates\decoration\client.js`):

```js
window.__ModuleLoader__.load({
  id: '@local/my-decoration',
  factory(require) {
    const React = require('react');
    const h = React.createElement;
    function Decoration() { … }
    return {
      inject: ['slots'],
      apply(ctx) {
        ctx.slots.inject('conversation.composer.dock', () => ctx.slots.register({
          name: 'conversation.composer.dock', id: 'my-decoration', order: 5,
        }, Decoration));
      },
    };
  },
});
```

  Both halves are plain ESM; there is **no build step required** for a hand-written plugin. *"For compiled sources, use the deployment's Client build tooling to emit this format; declare non-baseline runtime imports in `dsh.client.external`."* (`ui-plugin.md` L9)

#### Dependency-version rules

There are **two independent mechanisms**, and they behave differently:

1. **`peerDependencies` — enforced at install time.** Shipped packages pin `"@deepseek-ai/cordis": "~4.0.4"` (e.g. `dsh-client-ui-sidebar-browser\package.json` L42–44). Third-party plugins widen it (live `dshmarket\package.json`: `"@deepseek-ai/cordis": "^4.0.1"`, plus optional peers on `@deepseek-ai/dsh-settings` and `@deepseek-ai/schemastery`).
   `dsh-plugin-manager\README.md` L63: an install naming packages is checked **before pnpm runs** — *"a registry spec is resolved through pnpm's registry lookup for the version its range selects and the peers that version declares. An incompatible DSH peer rejects the operation before pnpm runs, so nothing is downloaded and no build script runs."* The refusal carries code `incompatible-version` with each refused package's `name`, `version`, `runtimeVersion`, and unsatisfied `peers` (L69). Git/tarball specs are judged **after** installation, and the profile manifest + lockfile are restored on rejection.
2. **`engines.dsh` — declarative only, NOT enforced.** `dsh-package-manifest\README.md` L93: *"Current installers and loaders do not enforce `dsh.manifestVersion` or `engines.dsh`; declaring a range does not reject incompatible hosts or validate SemVer syntax."*

**Exemptions** live in the profile's own `compatibility.json` beside `package.json` and `cordis.patch.yml`: *"an exact `package-name@version` mapped to a list of exact DSH runtime versions"* (README L65). Granted via `plugin_manager` `list_version_exemptions` → `set_version_exemption` with `target`, `runtimeVersion`, `acceptRisk: true` (after an explicit user warning), or CLI `dsh plugin --profile <p> allow-version …`.

The profile also sets `autoInstallPeers: false` (`C:\Users\haoch\.dsh\profiles\desktop\pnpm-workspace.yaml`).

#### How the plugin manager installs and enables

`plugin_manager` (tool) / `PluginManager` (service) / the Web **Plugins** page all drive one implementation (`dsh-plugin-manager\README.md`):

- **Install**: `install_bundle` with a registry name, absolute path, git address, or tarball. `inspect(spec, options)` pre-reads it; the answer carries *"the name, version, description, whether the package declares a bundle, and the `registry` that answered, or a `problem`: `invalid-spec`, `already-installed`, `not-found`, `not-a-package`, `not-a-bundle`, `network`, or `unknown`."* Registries are tried in turn (configured `registry`, then `fallbackRegistries` while a registry is unreachable / times out / answers not-found). pnpm runs with `--registry`.
- **Rollback**: *"A run that fails, is cancelled, or adds a package without a bundle patch restores `package.json` and `pnpm-lock.yaml` as they were."*
- **Build scripts**: pnpm 11-blocked dependency scripts surface as `pendingBuilds`; approval is granted through `approvedBuilds` on `install_bundle` *"after the user approves those scripts in the conversation"* and *"persists by package name in this profile."* The tool itself calls this out as a risk gate in its own description.
- **Enable/disable**: toggling a **plugin row** *"updates only `disabled` in the last matching override in the profile's `cordis.patch.yml`, or appends an override when none matches."* Toggling a **bundle** *"changes `package.json`'s ordered `dsh.profile.bundles` list… enabling appends the bundle at the end, which can change configuration precedence."* Appending on enable is a real footgun.
- **Liveness**: *"With HMR enabled in YAML, configuration changes apply immediately; without HMR, the running composition remains until restart."* *"Installing a new bundle can activate through HMR; replacing an installed package requires restart to load a fresh JavaScript module generation"* (`host-plugin.md` L60).
- **Events**: `plugin-manager/changed(change)`, `plugin-manager/install-log(chunk)`, `plugin-manager/install-state(progress)` — live signatures from the Host Event catalog.
- **Activation outcomes to read back**: `failed` (diagnose), `overridden` (a higher-priority layer wins), `restart-required` (not live).

### B. Client plugin API

#### What a Slot is

A **Slot** is a *parent-owned named extension position* in the Web render tree, declared by the component that renders it and occupied by child plugins. From `dsh-client-ui-slots\README.md` L28:

> "Compose UI through this package whenever you write a client plugin: register a component into a slot your parent declared, or declare child slots your component renders. The four kinds cover the composition shapes — `single` (one occupant), `list` (ordered entries), `keyed` (dispatch by a key), and `chain` (entries elect themselves)."

Hard rules (`dsh-client-ui-slots\lib\index.js` L163–243, error strings verbatim):

- `slot "<name>" is not declared (a parent entry's children table must declare it)` — you cannot register into an undeclared slot.
- `single` / `keyed` / `list` cells are per `(priority)` / `(key, priority)` / `(id, priority)`; a duplicate at the same priority throws. **"register at a different priority to shadow it (lowest renders)"**.
- `list` sorts by `priority` then `order`.
- Colours of scope: `root`, `session`, `session-maybe`. A `session` slot's props carry the current Session.
- *"Declaring a slot is claiming it: the registering entry becomes the only entry allowed to render that key"* (README L46).
- Disposal is automatic: *"An entry's disposer collapses its declared child slots recursively — ledger rows, contributions, and store mounts die on one lifecycle axis."*

The React-free core is `SlotCore`; the plugin-facing service wrapper (`ctx.slots`) lives in `@deepseek-ai/dsh-client-ui-renderer` and adds *"disposal through the caller's ctx.effect (fiber unload = cascade)… the registrant diagnostics stamp, and store-instance lifecycle on the entry axis."*

#### How a client plugin registers — the exact two-call idiom

```js
ctx.slots.inject(ownerKey, () => ctx.slots.register(options, Component))
```

`ctx.slots.inject` is documented in the live client catalog (`dsh-cordis-client-runner\lib\client.js` L1385) as:

> "Install an effect for each declaration lifetime of a slot. The callback runs synchronously when the declaration already exists; otherwise it runs inside the declaring `register()` call after the declaration is committed. Collapse disposes the effect and a later declaration runs it again."

`ctx.slots.register(options, component)` — the options are `{ name, key?, id?, order?, label?, priority?, select?, inject?, children?, store?, locale?, registrant? }`. Every catalog entry ships a generated `example`; the right-sidebar one verbatim:

```js
return {
  inject: ['slots'],
  apply(ctx) {
    ctx.slots.inject('sidebar.right.pane.tab', () => ctx.slots.register(
      { name: 'sidebar.right.pane.tab', key: '<one key the owner dispatches>' },
      () => React.createElement('div', null, 'hello'),
    ))
  },
}
```

Registered components receive **five framework prop shares** composed into one props object (README L38): the runtime share (`owner` from the parent's render call site + the session standard kit + global seat), the child-render share (`renderSlot`, statically narrowed), `renderFactorySlot`, the store share (`useStore` + baked actions, from `store: defineStore(...)`), and the business share inferred from `inject`.

#### How a right-sidebar **tab type** is declared and opened

Two stages, both inside the type's own `ctx.effect` (README L81–84):

```js
// 1. the type
ctx.sidebarRightTabs.register({
  id, kind, patterns?, priority?, canOpen?, title, guide?, keepMounted?
})   // → disposer

// 2. the body
ctx.slots.register({ name: 'sidebar.right.pane.tab', key: definition.id }, Body)
```

- `id` — *"this implementation's identity in the tab system, unique across every registration (a package name is the natural value…)"*; a second registration of an `id` throws. **`id` is also the slot `key`** for both the body and the title.
- `patterns` — globs over `dsh-resource://` addresses; one containing `:` matches the whole address (`dsh-resource://file/**`), one without matches the URI path at any depth (`*.md`). A **page type** names none and is opened by kind.
- `priority` band — `extension` (third-party, **highest, and the default when none is named**) > `builtin` > `fallback`. Then matched-pattern length, then registration order.
- `multiple: true` for independent instances (terminals).
- `keepMounted: true` retains visited bodies across tab/Session changes, collapse, and docking.

Navigation controller (`ctx.sidebarRight`):

```ts
openResource(address, options?)   // dsh-resource://<type>/… ; options: { kind?, params?, paneId?, replaceTab?, revealIfOpened?, preferNewPane? }
openTab(kind, options?)
close(tabId) · active() · focus(tabId) · split(paneId?) · float(tabId, rect?) · dock(paneId)
isExpanded() · toggleExpanded() · toggleFullscreen(target)
```

`openResource` with an address no type claims, or `openTab` with a kind nothing registered, **throws** — *"that is a wiring mistake, not a user error."* The panel expands on open: *"content the user cannot see is not opened."*

Also relevant: `sidebarRight.registerCloseHandler(kind, handler)`, and `ctx.sidebarRight.openTabs` publishes stable metadata for every open tab.

#### Plain-JavaScript builtins exposed to a client plugin

Two different answers depending on how the client half is authored.

**(a) Dynamic client half** (model-authored / `cordis_run`) — `CLIENT_BUILTIN_INSPECTION` L6141–6176, verbatim:

|---|---|---|
| `ctx` | "Restricted Cordis Context. Prefer ctx.get(name) with an undefined check; use inject only for hard dependencies." | `ctx.get(name): unknown \| undefined`, `ctx.on(name, listener): () => void`, `ctx.provide(name, value): () => void`, `ctx.effect(callback, label?): () => void` |

| `host` | "Package-private JSON RPC from Client to this Package's Host half." | `host.call(method: string, args?: JsonValue): Promise<JsonValue>` |

### C. Host plugin API

#### Registering a Tool

Service: `tools` — *"Tool registry and execution pipeline. Scoped registrations shadow globals; one visibility resolver feeds presentation, lookup, and dispatch."* Access via `ctx.tools` (`inject: ['tools']`) or `ctx.get("tools")` with an undefined check.

```ts
register(definition: ToolDefinition): () => void
```

*"Register globally or in the calling agent scope. Scoped tools shadow globals; duplicates within one layer and the reserved `run_code` name fail."* Returns *"the exact disposer that unregisters the tool."*

`ToolDefinition` (live contract, verbatim):

```ts
export interface ToolSchema {
    deferLoading?: true;
    name: string;
    description: string;
    parameters: Record<string, unknown>;   // JSON Schema (see JsonSchemaNode below)
}

export interface ToolDefinition extends ToolSchema {
    readonly output: ToolOutputDefinition;
    execute(args: unknown, exec: ToolRunContext): Promise<unknown>;
    projectContent?(exec: Readonly<ToolExecution>, result: Readonly<ToolExecutionResult>): ContentBlock[] | undefined;
    finalizeContent?(exec: Readonly<ToolExecution>, result: Readonly<ToolExecutionResult>): ContentBlock[] | undefined;
    timeoutMs?: number;
    isConcurrencySafe?(args: unknown): boolean;
    presentCall?(args: unknown): ToolCallView | undefined;
    presentResult?(args: unknown, result: ToolResult): ToolResultView | undefined;
}

export interface ToolOutputDefinition {
    readonly schema: JsonSchemaNode;
    render(args: unknown, value: JsonValue): ContentBlock[];
    presentationMeta?(args: unknown, value: JsonValue): JsonValue;
}

export interface ToolRunContext extends ToolExecution {
    deferContext(context: UserMessage): void;
    concludeTurn(): void;
}

export interface ToolExecutionInput {
    readonly callId: ToolCallId;
    readonly rootCallId?: ToolCallId;
    readonly name: string;
    readonly schema?: ToolSchema;
    readonly arguments: unknown;
    readonly agent?: Agent;
    readonly parent?: ToolExecutionToken;
    readonly signal: AbortSignal;
}
```

Note `parameters` is **plain JSON Schema** (`Record<string, unknown>`), and `output.schema` is a `JsonSchemaNode` — DSH does *not* require zod/schemastery for a tool.

Result shaping: `ToolExecutionResult` is a discriminated union on `isError`; success carries `value`, `content: ContentBlock[]`, optional `meta`, optional `additionalContexts?: UserMessage[]`, and optional `concludesTurn?: true`. **`additionalContexts` and `defersContext(context)` are the documented ways a tool feeds extra model-visible messages back into the loop.**

Other `tools` service members: `presentAs(mode: 'native'|'ptc'|'both')`, `restrict({allow?, deny?})`, `guard((exec) => string | undefined)`, `get(name, scope?)`, `schemas(scope?)`, `executionMode(exec)`, `execute(exec)`.

**Tool-UI rendering.** A tool's own presentation comes from `presentCall` / `presentResult` returning `ToolCallView` / `ToolResultView` (`card: 'generic'|'terminal'|'diff'|'read'|'search'|'web'`). On the client, the card is overridable through the `tool.call.toolview` slot, **keyed by the wire tool name** — the live occupants list shows one row per shipped tool (`AskQuestionRow key 'ask_user_question'`, `BashRow key 'bash'`, `PresentRow key 'present'`, etc.).

#### Registering Services and listening to Events

DSH host plugins are **Cordis 4** plugins. The loader is `@deepseek-ai/cordis-plugin-loader`; the DSH-side runners are `@deepseek-ai/dsh-cordis-host-runner` and `-client-runner`.

- **Plugin form**: `export function apply(ctx, config)`, optional `export const inject = [...]`, optional `export const Config` — verified for every shipped host package through the live `Service.listService` output, whose access recipes are generated as:
  - optional: `ctx.get("service")`, `requiresUndefinedCheck: true`
  - hard dependency: `inject: ["service"]` → `ctx.service`
- **Registering a service**: `ctx.provide(name, value)` (visible in the restricted-`ctx` builtin list as `ctx.provide(name: string, value: unknown): () => void`). DSH's own packages extend Cordis's `Service` base class — e.g. every abstract service in the catalog (`attachments`, `compaction`, `credentials`, `fs`, `shell`, `subprocess`, `web`) is declared with `abstract` members and registered under a fixed key. `dsh-cordis-host-runner\lib\registry.js` and `lifecycle.js` are the DSH-side registration/lifecycle layer.
- **Events**: `ctx.on(name, listener)`. The live Host Event catalog reports each event's **dispatch mode**, which determines what a listener may do:

| Mode | Meaning | Example from the catalog |
|---|---|---|
| `emit` | fire-and-forget notification | `'tools/result'(this: Scoped<ToolRuntime>, exec, result): undefined` |
| `serial` | awaited in order, no veto | `'agent/created'(…): undefined \| Promise<undefined>` |
| `parallel` | all listeners awaited | `'session/flush'(this: Scoped<Session>, session): Promise<void> \| void` |
| `waterfall` | listener gets `next()`; may rewrite or short-circuit | `'tools/pre-execute'(this, exec, next: () => Promise<PreToolDecision>): Promise<PreToolDecision>` |

**Context injection — the two real APIs.**

1. **System prompt (global or per-scope), via `ctx.systemPrompt`:**

```ts
section(section: PromptSection): () => void
context(context: PromptContext): () => void
variable(name: string, provider: (context: AssembleContext) => string | undefined): () => void
tools(provider: (context: AssembleContext) => ToolProviderResult): () => void
suppressRuntimeContext(): () => void
assemble(context?: AssembleContext): Promise<PromptAssembly>
```

```ts
export interface PromptSection {
    readonly name: string;
    readonly order: number;
    readonly text: string | ((context: AssembleContext) => string);
    readonly interpolate?: boolean;
    readonly complete?: boolean;
}
export interface PromptContext {
    readonly name: string;
    readonly order: number;
    readonly text: string | ((context: AssembleContext) => string);
}
export interface AssembleContext { scope?: ScopeKey; signal?: AbortSignal; }
```

*"Register an ordered prompt section in the calling context's scope. A scoped section shadows a global section with the same name; duplicates within one layer and non-finite orders throw. Registration and disposal emit `system-prompt/change`."*
`practices.md` L18 gives the normative rule: *"Add prompt text with `ctx.systemPrompt.section()`. Add per-agent context with `agent.inject()`… `agent/request` listeners cannot change request messages."* And L17: *"Do not listen to `system-prompt/assemble` to add or remove tools or text."*

2. **Per-agent context injection, via `Agent.inject`.** `dsh-agent\README.md` L47:

> "The handle's methods route identified user-role messages into the agent's inbox. `followup()` queues an ordinary next-turn prompt and wakes the driver; `steer()` submits next-step input and wakes it; **`inject()` adds model-facing context without waking the driver, so it lands in the next admitted step.**"

```js
handle.agent.followup({ content: [{ type: 'text', text: '…' }], source: { kind: 'user' } })
handle.agent.steer({ content: [{ type: 'text', text: '…' }], source: { kind: 'plugin', plugin: 'my-plugin' } })
await handle.agent.whenIdle()
```

`practices.md` L29 adds the practical consequence: *"A timer that starts work calls `agent.followup()`, which wakes the agent; `agent.inject()` does not wake it, so injected context can wait in the inbox until other input arrives."*
It is logged durably as `agent/inbox/spliced` (`dsh-agent\README.md` L89; the fold is owned by `dsh-agent-loop` and reconstructible — *"Reconstruction rejects unsafe or out-of-range splice coordinates and duplicate `MessageId` values across both pending lists."*)

**Injecting a tool result back into the conversation**: a `ToolDefinition.execute` has no direct "append message" call; the supported routes are the tool's own `content` return, `ToolExecutionSuccess.additionalContexts?: UserMessage[]`, and `exec.deferContext(context: UserMessage)` on `ToolRunContext`.

**Emitting UI updates to the client.** There is **no generic "push an event to the browser" service**. The architecture is:

- **Typert** is the client↔host RPC/schema mechanism. `typert` service: *"Registry of generated schemas, package reflection, invocations, and Remote dependency providers"* — `register(contribution)`, `get(key)`, `resolve(key)`, `list(filter)`, `getPackage(packageName, face: 'host'|'client')`, `toJSONSchema(key, params?)`. `typertGateway`: *"Resolve strict generated definitions or conservative SRC markers against current Cordis Services and Typert providers"* — `hasLiveClient()`, `invoke(request)`, `stream(request)`, `registerRemoteEvents(source, host)`.
- **`@Remote` decorators** on service methods are how a host service becomes client-callable: e.g. `commands.execute`, `goals.get`, `terminalController.create`, `workspaceFiles.read`. Both `@Remote('name')` (renamed export) and `@Remote({ mode: 'stream' })` (server-streaming) appear throughout the live catalog.
- **Client → its own Host half**: the `host.call(method, args?)` builtin (dynamic halves) — *"Package-private JSON RPC from Client to this Package's Host half."*
- **Shell-level updates**: `webServer.register(route)`, `registerUpgrade`, `registerFallback`, `tapIndex(transform)`, and the `webserver/index-inject` event (*"Collect the structured index injection table"*).
- **State reach** the client: `practices.md` L38 — *"When the Client needs a value derived from a session, declare `wire.view` on the Host projection. The value reaches the Client already computed; the Client does not fold session events itself."* **The exact `wire.view` declaration syntax is UNVERIFIED** — only this prose reference was found.

**Hard constraint on session writes** (`practices.md` L21):

> "Do not append session events with a new `type`. Readers accept an unknown stored event only when its envelope carries `ignorable: true`, and live `Session.append()` cannot set that marker, so the Session would refuse to reopen. Derive state from existing events, or keep plugin-owned data in a storage service found through inspection."

So: **no, you cannot add a custom message type to the session log.** Use `systemPrompt.section/context`, `agent.inject()`, a tool's `content`/`additionalContexts`, or your own storage.
